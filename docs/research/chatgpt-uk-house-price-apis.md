## USER

Are APIs for UK house prices available? I know the information is public, but what’s the best way to access it? 


---

## ASSISTANT

Yes. For **actual sold prices in England and Wales**, the best source is HM Land Registry’s **Price Paid Data (PPD)**. It’s the underlying public dataset behind much of what you see on property websites: sale price, completion date, address/postcode, property type, new-build status, freehold/leasehold, etc. It covers transactions back to **1995** and is updated monthly. 

There are essentially three useful ways to consume it:

1. **Bulk CSV — probably what I'd use for a serious application.** Land Registry publishes yearly files (~100–200 MB/year) or a single ~5.3 GB CSV containing the complete history.   
   

2. **Linked Data queries — better for ad-hoc queries.** Land Registry exposes PPD as machine-readable linked data, so you can query subsets rather than downloading billions of bytes. Their own report builder sits over this sort of data. 

3. **UK House Price Index — for market trends rather than individual houses.** If you're asking things like *"how have prices in Barnet changed since 2020?"*, UK HPI is much better. It provides aggregated/indexed data by geography and property type, with CSV downloads and historical series. 

One important distinction: Land Registry does have a conventional **REST/JSON API**, but its documented "Use land and property data" API is primarily for accessing datasets such as ownership, polygons, leases and covenants; it isn't simply a nice `GET /property/price?postcode=...` API for Price Paid Data. 

For something you're building yourself, I'd probably **download PPD and put it into a local database**. For example, PostgreSQL/DuckDB/SQLite could trivially support:

```text
postcode = "N11 2XX"
↓
all transactions
↓
12 SOME ROAD       £410,000   2016
12 SOME ROAD       £515,000   2020
14 SOME ROAD       £535,000   2021
16 SOME ROAD       £560,000   2023
```

Then combine that with **UK HPI** to estimate today's value:

```text
last sale price
      ×
HPI(current date) / HPI(sale date)
      =
rough current valuation
```

You can get considerably more sophisticated by finding comparable nearby properties with the same type/tenure, weighting recent sales more heavily, etc. This is effectively the beginnings of an automated valuation model.

There's even now a **UPRN lookup dataset** mapping Land Registry transaction IDs to Unique Property Reference Numbers, which makes joining property data from different government datasets substantially nicer. 

So if your thought is *"could I programmatically look at my house, neighbouring sales and local price movements?"* — **absolutely**. The raw data is unusually accessible, and you don't need to scrape Rightmove or Zoopla. The only wrinkle is that recent transactions lag registration: Land Registry says the delay is typically around **2 weeks–2 months**, so the newest months are incomplete. 

If you tell me what you're thinking of building, I can suggest the cleanest data/API architecture for it.

Yes. The useful mental model is: **don't start by designing for scale**. Start with one PostgreSQL instance on a Linux machine, but arrange things so that each scaling step is incremental rather than requiring a rewrite.

# 3. Import Land Registry PPD

A simplified table might look something like:

```sql
CREATE TABLE transactions (
    transaction_id UUID PRIMARY KEY,
    price INTEGER NOT NULL,
    sale_date DATE NOT NULL,

    postcode TEXT,
    property_type CHAR(1),
    new_build BOOLEAN,
    tenure CHAR(1),

    paon TEXT,
    saon TEXT,
    street TEXT,
    locality TEXT,
    town TEXT,
    district TEXT,
    county TEXT
);
```

Then bulk import the Land Registry CSV.

Postgres `COPY` is extremely fast:

```sql
COPY transactions
FROM '/data/pp-complete.csv'
WITH (FORMAT csv);
```

Five gigabytes of source CSV is really not a large database problem.

Once imported, the PostgreSQL representation might be on the order of **10–20 GB**, depending on schema/indexes. That's tiny by database-server standards.

---

# 4. Indexing is where the magic happens

Without indexes:

```sql
SELECT *
FROM transactions
WHERE postcode = 'N11 2AB';
```

potentially means:

> Go through tens of millions of transactions looking for N11 2AB.

That's obviously poor.

So:

```sql
CREATE INDEX idx_transactions_postcode
ON transactions(postcode);
```

PostgreSQL builds a B-tree.

Now:

```sql
SELECT *
FROM transactions
WHERE postcode = 'N11 2AB';
```

is extremely cheap.

You'd probably eventually have indexes such as:

```sql
CREATE INDEX idx_postcode
ON transactions(postcode);

CREATE INDEX idx_sale_date
ON transactions(sale_date);

CREATE INDEX idx_postcode_date
ON transactions(postcode, sale_date);

CREATE INDEX idx_property_type
ON transactions(property_type);
```

But don't blindly index every column: indexes consume storage and make inserts/updates more expensive.

---

# 5. Add coordinates

This is where **PostGIS** becomes particularly useful.

You could obtain postcode coordinates from ONS/open postcode data and attach a geographic point:

```text
N11 2AB → 51.61..., -0.13...
```

Then:

```sql
location GEOGRAPHY(POINT, 4326)
```

Suddenly your API can ask:

```text
Find all detached houses
sold within 750 metres
during the last 24 months
```

and PostGIS can execute that efficiently using a spatial index.

Conceptually:

```sql
CREATE INDEX idx_location
ON properties
USING GIST(location);
```

That is exactly the kind of query I'd want for a house-price system.

# 6. Put an API in front

**Don't expose PostgreSQL to users.**

Instead your application exposes:

```text
GET /property/N11-2AB/14
GET /sales?postcode=N11-2AB
GET /sales?lat=51.61&lon=-0.13&radius=500
GET /estimate/12345678
```

FastAPI might translate one of those into:

```sql
SELECT *
FROM transactions
WHERE postcode = $1
ORDER BY sale_date DESC;
```

The browser/mobile app never knows your database credentials.

You now have:

```text
Client
  │
  │ HTTPS
  ▼
API
  │
  │ private connection
  ▼
PostgreSQL
```

This separation becomes important when you scale.

# 7. The part that initially seems mysterious: scaling

Suppose your little server becomes popular.

You **don't** normally respond by immediately chopping your database into 20 servers.

You scale progressively.

### Stage A — bigger machine

Perhaps:

```text
4 CPU / 8 GB
       ↓
8 CPU / 32 GB
```

This is called **vertical scaling**.

PostgreSQL can handle surprisingly serious workloads on one good machine.

For a property-price website, you could potentially serve a very substantial user base this way.

### Stage B — separate API and database

Move from:

```text
┌──────────────────┐
│ Linux server     │
│                  │
│ API              │
│ PostgreSQL       │
└──────────────────┘
```

to:

```text
 API server
      │
      ▼
 Database server
```

Now they can scale independently.

### Stage C — multiple API servers

The API should ideally be **stateless**.

So you can do:

```text
                   ┌── API 1 ──┐
                   │           │
Internet → LB ─────┼── API 2 ──┼──→ PostgreSQL
                   │           │
                   └── API 3 ──┘
```

A load balancer distributes requests.

Going from:

```text
1 API process
```

to:

```text
50 API processes
```

can therefore require almost no architectural change.

This is **horizontal scaling**.

---

# 8. Eventually PostgreSQL becomes the bottleneck

But there's another useful property of your application:

**house-sale history barely changes.**

Most requests are reads.

So eventually:

```text
                    ┌── PostgreSQL replica
                    │
Primary PostgreSQL ─┼── PostgreSQL replica
                    │
                    └── PostgreSQL replica
```

Imports happen on the primary.

Queries can go to replicas.

Now your read capacity scales horizontally too.

---

# 9. Then introduce caching

Imagine thousands of people request:

```text
/property/N11-2AB/14
```

There's no reason to execute the same database query every time.

You introduce Redis:

```text
                ┌─────────┐
                │  Redis  │
                └────┬────┘
                     │
Client → API ────────┤
                     │ cache miss
                     ▼
                PostgreSQL
```

First request:

```text
API → Redis

MISS

API → PostgreSQL
API → Redis: store result for 1 hour
```

Next thousand:

```text
API → Redis → result
```

PostgreSQL never sees them.

For relatively static property data, caching can be **extremely effective**.

In firmware we're often forced to make architectural decisions early because:

```text

flash
CPU
hardware interfaces
```

are effectively fixed forever.

Server software is different.

I'd build **this**:

```text
            £20–50/month VM
                   │
        ┌──────────┴──────────┐
        │                     │

                              +
```

and deliberately *not* implement:

```text
✗ Redis
✗ database sharding
✗ read replicas
✗ microservices

✗ distributed databases
```

until measurement says you need them.

You might discover your £30/month PostgreSQL box happily handles the entire workload.

## The scale involved is probably smaller than you're imagining

This particular dataset is a nice first backend project because **UK residential transactions are not "big data."**

You're dealing with tens of millions of relatively small records, not trillions of events.

A modern PostgreSQL server with sufficient RAM and sensible indexes is extraordinarily capable at that scale. You can have a database much larger than RAM because PostgreSQL + Linux's page cache keep the frequently accessed pages hot.

So I'd think about your first version approximately as:

```text

          │
          ▼
    Import script
          │
          ▼

          │
          ▼
     Python API
          │
          ▼
       HTTPS
          │
          ▼
    Web application
```

**That is a perfectly legitimate production architecture.**

And the really nice part is that practically every scaling step from there — bigger DB → separate DB → multiple API instances → cache → read replicas — can happen without changing the fundamental data model or rewriting the application.

## USER

Realistically how much traffic could my one server handle? 1000 visitors a day? 


---

## ASSISTANT

Easily. **1,000 visitors/day is tiny** for a sensibly built application on a modern 4-vCPU/8-GB Hetzner VM.

Consider what 1,000 visitors/day actually means. If each visitor makes 20 API requests, that's 20,000 requests/day, or an average of only **0.23 requests/second**. Even if your peak traffic is 20× the average, you're still talking about ~5 requests/second.

A PostgreSQL-backed API doing indexed queries like:

```sql
SELECT *
FROM transactions
WHERE postcode = $1
ORDER BY sale_date DESC;
```

can typically handle **hundreds or potentially thousands of such requests per second**, depending heavily on query complexity, caching, connection handling and hardware. Your web/API layer is unlikely to be the limiting factor either.

So roughly, I'd think about the orders of magnitude like this:

| Usage | One decent VM |
|---|---|
| 100 visitors/day | Barely noticeable |
| **1,000/day** | **Trivial** |
| 10,000/day | Very comfortable |
| 100,000/day | Quite plausible with good architecture |
| 1M/day | Now I'd start thinking seriously about load, caching and separation |

And there's another advantage in your particular application: **the data is predominantly read-only**.

A request such as:

```text
"Show me sales around N11 2XX"
```

is an ideal database workload. PostgreSQL can keep commonly accessed indexes/data in RAM, and Cloudflare can potentially cache API responses above it.

At 1,000 visitors/day your architecture could quite happily remain:

```text
                 Cloudflare
                     │
                     ▼
             Hetzner 4c / 8GB
          ┌────────────────────┐
          │                    │
          │ Caddy/nginx        │
          │      ↓             │
          │ FastAPI            │
          │      ↓             │
          │ PostgreSQL/PostGIS │
          │                    │
          └────────────────────┘
```

You wouldn't need Redis, Kubernetes, multiple API servers, database replicas or any of that.

In fact, **RAM would probably matter more than CPU** for this workload. PostgreSQL benefits enormously from filesystem/database caching. An 8–16 GB machine with fast NVMe and sensible indexes could punch surprisingly far above what you'd intuitively expect from embedded systems.

The point where I'd change architecture wouldn't be "*we've reached 1,000 users*." I'd monitor things like CPU utilisation, RAM/cache pressure, PostgreSQL query latency, disk I/O, API p95/p99 latency and concurrent DB connections. **Scale when those numbers tell you to.**

There's also an important distinction between **1,000 visitors/day and 1,000 simultaneous visitors**. The latter is a much more interesting engineering problem. But even then, it doesn't necessarily mean 1,000 simultaneous database operations—HTTP requests are short-lived.

So if this property project unexpectedly became popular, I wouldn't be remotely concerned about the initial Hetzner architecture. You could probably grow by **orders of magnitude** before needing a fundamentally different design.

```text
                Caddy       │
                  │         │
                FastAPI     │
                  │         │
              PostgreSQL    │
              localhost     │
                            │
Laptop ───── Tailscale ─────┘
              SSH
```

The important protections would be:

- **Hetzner firewall:** only permit the traffic you actually need.
- **SSH keys only:** disable password authentication and root SSH login.
- **Tailscale for administration:** ideally SSH isn't exposed publicly at all.
- **PostgreSQL bound to localhost/private interface:** port 5432 never touches the Internet.
- **Cloudflare in front of HTTP:** your public service gets their proxying, DDoS protection and other edge-security features.
- **Ubuntu unattended security upgrades:** automatically install important security patches.
- **Application runs unprivileged:** FastAPI etc. absolutely shouldn't be running as root.
- **Backups:** security includes recovering from your own mistakes, not merely attackers.

One subtle point is particularly important: **Cloudflare doesn't automatically protect your origin if attackers can simply connect directly to the Hetzner IP.**

Eventually you can configure the Hetzner firewall so your web server accepts HTTP(S) only from Cloudflare's network ranges:

```text
Internet
   │
   ├──→ 123.45.67.89:443       ❌
   │
   ▼
Cloudflare
   │
   └──→ 123.45.67.89:443       ✓
```

Then your actual server is much less exposed.

For administration I'd do essentially the same thing:

```text
Internet → server:22            ❌

Your laptop
    │
 Tailscale
    │
    ▼
server:22                       ✓
```

That leaves an extremely small attack surface.

### What Hetzner handles vs what you handle

Hetzner is responsible for things below your VM: datacentre security, physical servers, hypervisor/cloud infrastructure, network infrastructure and so forth.

You're responsible for essentially everything **inside Ubuntu**:

```text

SSH configuration
users/permissions
firewall policy
PostgreSQL security
web-server configuration
application vulnerabilities
secrets/API keys
backups
```

It's the classic **shared-responsibility model**.

But I wouldn't let that put you off. A single-purpose Ubuntu server is actually refreshingly understandable from a security perspective. You can get to a very respectable baseline with perhaps an hour of initial configuration.

And because you're already comfortable with Linux, I'd much rather see you running a deliberately locked-down Ubuntu VM than adopting a complicated AWS architecture under the assumption that AWS somehow makes the application inherently secure.

When we create the Hetzner box, I'd suggest we build it **secure-by-default from the beginning**: SSH key → non-root user → Tailscale → firewall → automatic security updates → Docker/application isolation → PostgreSQL localhost-only → backups. That avoids having to retrofit security later.
